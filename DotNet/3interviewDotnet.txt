-> what are generations in garbage collection
    - Objects that are newly created are more likely to become unreachable quickly, while objects that survive several collections are more likely to continue living.
    - In .NET, the Garbage Collector (GC) divides managed objects into generations based on how long they have survived
    - Dot NET GC uses three generations: Gen 0, Gen 1, and Gen 2. New objects generally start in Gen 0. If they survive a collection, they can be promoted to Gen 1 and 
        eventually Gen 2. Gen 0 is collected most frequently because most objects are short-lived, while Gen 2 is collected less frequently because it contains longer-lived 
        objects. This generational approach reduces the amount of memory the GC has to examine and improves application performance. Large objects are placed on the Large 
        Object Heap and are generally collected with Gen 2

=> SOLID principes :: Principles are guidelines for how you should design code.They help you make better design decisions.
    - what is Single Responsibility Principle
        - An SRP states that a class should have only one responsibility or a class should have only one reason to change.
        - when a class have one responsibility, it is easier to understand, maintain, and test. It also promotes code reusability and reduces the risk of introducing bugs when making changes.
    - O — Open/Closed Principle
        - Software should be open for extension but closed for modification.
        - Instead of repeatedly modifying existing code for every new behavior, design it so new behavior can be added through abstractions.
    - L — Liskov Substitution Principle
        - A derived class should be usable wherever its base class is expected without breaking the expected behavior.
        - LSP states that objects of a superclass should be replaceable with objects of a subclass without affecting the correctness of the program
        - If a child class needs to throw exceptions or behave unexpectedly for functionality promised by the parent, the inheritance hierarchy is probably wrong.
        - LSP is not simply "inheritance should work"; it's about behavioral compatibility between the parent and child.
    - I — interface segregation principle
        - ISP states that clients should not be forced to depend on interfaces they do not use. In other words, an interface should have only the methods that are relevant to the implementing class.
    - D — Dependency Inversion Principle
        - High-level modules should not depend on low-level modules. Both should depend on abstractions.
        - High-level module Contains business rules/use cases.Low-level module Contains implementation details
        - For example, instead of an OrderService directly depending on SqlOrderRepository, I would define an IOrderRepository abstraction and inject it into OrderService

=> Difference between Abstraction and Encapsulation :: Abstraction focuses on hiding implementation complexity and exposing only the essential behavior, commonly using 
   interfaces and abstract classes. Encapsulation focuses on protecting an object's internal state by restricting direct access and exposing controlled operations through methods or properties.
-> Method overriding vs method hiding : Method overriding occurs when a derived class provides a new implementation for a virtual or abstract base method. The method is selected at runtime 
   based on the actual object type. Method hiding uses the new keyword to define a method with the same name in the derived class, and the method selected depends on the reference type.
-> Abstract class does not support multiple inheritance 
    - A class cannot inherit from multiple classes, But it can implement multiple interfaces
-> OOP in C# is based on four main concepts: encapsulation, abstraction, inheritance, and polymorphism. Encapsulation protects an object's internal state. Abstraction hides implementation 
   details and exposes essential behavior. Inheritance allows a class to reuse or extend another class's functionality. Polymorphism allows the same interface or base reference to behave 
   differently depending on the implementation, such as method overriding at runtime or method overloading at compile time.
    - Encapsulation means bundling data and behavior together and controlling access to the internal state.
    - Abstraction means exposing only the essential behavior while hiding implementation details.

-> Deferred Execution vs. Immediate Execution in LINQ
    - In .NET, deferred (lazy) execution and immediate execution define when a query is actually run, while IEnumerable and IQueryable define how and where that query is processed.
    - The core link between them is that both IEnumerable and IQueryable default to deferred execution, but they handle immediate execution differently based on where the data lives.
    - Because of deferred execution, you can keep appending filters (like .OrderBy() or .Take()) to both types without hitting the data source multiple times
    - Deferred execution: LINQ query executes when you actually enumerate the result.
        - Where(),Select(),OrderBy(),ThenBy(),Skip(),Take() - Generally, these return another query rather than immediately materializing the results.
        - Deferred execution can execute multiple times.The query can execute again during the second enumeration.If the underlying source is a database query with EF Core, this can potentially mean multiple database queries.
            - we need to explicitly materialized using methods like ToList()
    - Immediate execution: LINQ query executes immediately and produces a concrete result.
        - ToList(),ToArray(),Max(),Min(),Sum(),Average(),Single(),Any(),All() - 
-> IEnumerable vs IQueryable
    - IEnumerable<T> is mainly used for in-memory collections
    - IQueryable → build a query that can be translated and executed by the data source, usually the database
    - Why is IQueryable generally better for database queries?
        - Because filtering, sorting, projection, etc. can be translated into SQL and executed by the database instead of loading unnecessary data into application memory.
-> Finalize vs Dispose
    - Dispose() → you explicitly release resources.
    - Finalize() → the GC eventually gets a chance to release unmanaged resources.
    - Dispose provides deterministic cleanup through IDisposable, and we normally use it with using or using var. A finalizer is non-deterministic 
      and is invoked by the GC's finalization mechanism. It is mainly a safety net for unmanaged resources if deterministic cleanup wasn't 
      performed. We generally avoid writing finalizers ourselves when possible and prefer SafeHandle. When Dispose successfully cleans up 
      resources, GC.SuppressFinalize(this) prevents unnecessary finalization.

-> How Would You Implement Rate Limiting in a .NET API?
    - Rate limiting controls how many requests a client can make within a given period. In ASP.NET Core, I'd use the built-in Microsoft.AspNetCore.RateLimiting 
      middleware, choose a policy such as Fixed Window, Sliding Window, Token Bucket, or Concurrency Limiter depending on the endpoint, and return HTTP 429 Too Many Requests when the limit is exceeded.
    - So for a distributed environment, you may need a distributed rate limiter/state store, commonly something like Redis, depending on your architecture and consistency requirements
    - Internet -> WAF / DDoS protection -> Load Balancer -> ASP.NET Core rate limiting -> API -> Database
-> Two Users Submit Conflicting Price Updates Simultaneously. How Do You Handle This?
    - For most CRUD APIs, I'd use optimistic concurrency :: EF Core includes RowVersion in the WHERE clause. If another user changed the row, it 
      throws DbUpdateConcurrencyException, and I return 409 Conflict with a ProblemDetails response telling the client to refresh and retry
    - This is a lost-update problem, so I'd use optimistic concurrency for a typical product API. I'd add a concurrency token such as SQL Server's 
      rowversion to the Product entity. When the client reads the product, it also gets the current version. When it updates, EF Core includes 
      that version in the update condition. If another user has already modified the row, the version no longer matches, so EF Core throws 
      DbUpdateConcurrencyException. I'd catch that and return an appropriate conflict response, typically HTTP 409, so the client can refresh 
      and let the user decide how to resolve the conflict.
=> Your EF Core Query Works with 100 Records but Times Out with 100,000. How Do You Fix It?
    - Inspect the generated SQL and execution plan first, then optimize filtering, indexing, projection, joins, pagination, tracking, and database access.
    - 1. Reproduce the slow query -> 2. Inspect generated SQL -> 3. Run SQL directly against DB -> 4. Inspect execution plan -> 5. Check indexes
      6. Check joins / N+1 -> 7. Check filtering & projection -> 8. Add pagination -> 9. Use AsNoTracking for read-only queries ->10. Check DB blocking/resources
      11. Consider caching -> 12. Only then consider timeout adjustment
-> Indexing : modelBuilder.Entity<Product>().HasIndex(p => new { p.CategoryId, p.IsActive });
    - HasIndex creates a database index. Here I'm creating a composite index on CategoryId and IsActive because queries frequently filter products 
      using both columns. This allows the database to locate matching rows more efficiently instead of scanning the entire table. The order of 
      columns in a composite index matters, so I choose it based on the application's query patterns.

-> How Do You Prevent Mass Assignment (Over-Posting) Attacks
    - I prevent mass assignment by never binding API requests directly to my EF Core entities. I use dedicated request DTOs that contain only the 
      properties the client is allowed to modify, and explicitly map those properties to the entity. For sensitive fields like roles, admin status, 
      or balances, I use separate authorized operations or policies. I also don't trust client-supplied IDs or security-sensitive properties.

-> What's Vertical Slice Architecture vs Clean Architecture ?
    - Clean Architecture organizes an application around technical layers such as API, Application, Domain, and Infrastructure, with dependencies 
       pointing toward the domain. Vertical Slice Architecture organizes the application around business features or use cases, so everything 
       required for a particular feature is kept together. Vertical Slice generally reduces unnecessary abstractions and makes feature changes 
       easier to isolate. They can also be combined—for example, using vertical slices for feature organization while still keeping domain and 
       infrastructure boundaries.
-> For modern ASP.NET Core applications, Vertical Slice + MediatR/CQRS + EF Core is a common combination, especially when the application has many independent business features.
