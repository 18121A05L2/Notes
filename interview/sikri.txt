-> A typical Agile project can look like this end to end: - 
   Business Idea -> Requirements / Product Backlog -> Epic → User Stories → Tasks -> Sprint Planning -> 
   Development -> Code Review -> CI/CD + Testing -> QA / UAT -> Sprint Review -> Release -> Retrospective -> Next Sprint
  - The Product Owner breaks the requirement into smaller pieces. Priority of the tickets decided by the product owner
  - An Epic is a large business capability. A user story describes functionality from the user's perspective.. A Task is a technical step to complete a User Story.
  - All the stories/features that need to be built go into the Product Backlog.
  - Backlog Grooming :: Before a sprint, the team discusses upcoming stories.This is often called Backlog Refinement or Backlog Grooming.
  - Estimation :: The development team estimates the complexity of stories. A common Agile technique is Story Points.
  - For story point :: A team might use: 1, 2, 3, 5, 8, 13, 21. This is commonly based on the Fibonacci sequence. 
  - Sprint Planning :: The team looks at the prioritized backlog and decides what can realistically be completed during the sprint.
  - Sprint Review :: At the end of the sprint, the team demonstrates the completed functionality to stakeholders.
  - Sprint Retrospective :: After the sprint, the team discusses how the team worked, rather than what product functionality was delivered.
    - What went well? , What didn't go well? , What should we improve?
  - Daily Scrum / Stand-up 
    - What did I do yesterday? , What will I do today? , Do I have any blockers?

=> You can explain an Agile project in one flow:
    - Business requirements are converted into epics and user stories, which are prioritized in the product backlog. During refinement, the team 
      clarifies requirements and estimates the stories. In sprint planning, the team selects stories for the sprint and breaks them into technical 
      tasks. Developers implement the stories, write tests, create pull requests, and go through code review and CI/CD. QA validates the functionality 
      against acceptance criteria. Completed work is demonstrated during the sprint review, and the team discusses process improvements during the 
      retrospective. Feedback and new requirements go back into the backlog, and the cycle repeats until the product is delivered.

-> Q. What is used for creating a JWT token, including the payload, header, and signature?
  - A JSON Web Token (JWT) is created from three parts: a Header (specifies token type and signing algorithm, e.g., HS256 or RS256), a 
    Payload (claims like sub, exp, roles), and a Signature (verifies integrity). The header and payload are Base64URL encoded and concatenated, 
    then the signature is generated by signing that string with a secret (symmetric, e.g., HMAC SHA) or a private key (asymmetric, e.g., RSA or ECDSA).
  - In practice you use a JWT library for your platform (e.g., jsonwebtoken for Node.js, jjwt for Java, PyJWT for Python) and provide: the claims, the 
    chosen algorithm, and the secret/private key plus optional settings like expiration (exp) and issuer (iss). The library handles encoding and 
    signing, producing the final token.

-> What are chunking methods which we could use and how would you choose which chunking method would you use?
  - A good chunk should contain enough context to answer a question, but be small enough that retrieval can identify it accurately
  - Fixed-size chunking - Split the document based on a fixed number of characters or tokens.
    - Good for: simple text, logs, large unstructured documents.
  - Sentence-based chunking - Instead of cutting based on tokens, split around sentences.
    - Good for: Articles, Documentation, General text, Knowledge bases
  - Paragraph-based chunking - Split according to paragraphs.
    - Good for: Technical documentation, Markdown, FAQs, Internal company documentation
  - Recursive chunking - This is one of the most commonly used approaches in practical RAG systems.
    - Recursive chunking is an AI text-splitting strategy that breaks large documents into smaller pieces by testing a prioritized list of 
      natural separators—such as paragraphs, lines, words, and characters—until every chunk fits a target size
    - Good default choice for general-purpose RAG.
  - Semantic chunking - Semantic chunking tries to determine where the meaning/topic changes, rather than using fixed boundaries.
  - Document-structure-based chunking - For structured documents, you should often use the document's structure rather than generic chunking.
  - Code-aware chunking - For source code, normal text chunking is usually a bad idea.
  - How do I choose the chunking method?
